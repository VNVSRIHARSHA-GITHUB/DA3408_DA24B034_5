# Part A --- REST Service (FastAPI)

**Directory:** `partA/`

`eta_app.py` serves the model at `POST /v1/models/eta:predict`, with
`GET /healthz` and `GET /metrics`. The model file is chosen with the
`ETA_MODEL` environment variable (default `data/eta_v1.joblib`).

### Run the Tests (A2)

``` bash
pytest partA -v
```

Expected: **24 passed**.

### Start the Service

``` bash
ETA_MODEL=data/eta_v1.joblib uvicorn eta_app:app --app-dir partA --port 8000 --no-access-log
```

In another terminal:

``` bash
curl http://localhost:8000/healthz
```

``` bash
curl -X POST http://localhost:8000/v1/models/eta:predict \
  -H "Content-Type: application/json" \
  -d '{"instances": [{"distance_km": 12.5, "n_stops": 4, "hour": 10, "weekday": 2, "traffic_index": 0.3, "rain": 0, "weight_kg": 5.0}]}'
```

### Load Test (A3)

With the 1-worker server above running:

``` bash
python load_test.py --url http://localhost:8000/v1/models/eta:predict --data data/eta_sample.csv --concurrency 1 2 4 8 16 --duration 4 --out partA/loadtest_results.json
python load_test.py --url http://localhost:8000/v1/models/eta:predict --data data/eta_sample.csv --concurrency 1 --duration 4 --batch 1 --out partA/loadtest_batch1.json
python load_test.py --url http://localhost:8000/v1/models/eta:predict --data data/eta_sample.csv --concurrency 1 --duration 4 --batch 100 --out partA/loadtest_batch100.json
```

Restart the server with two worker processes (the A3.4 change):

``` bash
ETA_MODEL=data/eta_v1.joblib uvicorn eta_app:app --app-dir partA --port 8000 --workers 2 --no-access-log
```

``` bash
python load_test.py --url http://localhost:8000/v1/models/eta:predict --data data/eta_sample.csv --concurrency 1 2 4 8 16 --duration 4 --out partA/loadtest_workers2.json
```

Build the report tables:

``` bash
python partA/analyze_load.py partA/loadtest_results.json
python partA/analyze_load.py partA/loadtest_batch1.json partA/loadtest_batch100.json --batch 1 100
python partA/analyze_load.py partA/loadtest_results.json partA/loadtest_workers2.json --compare
```

### Results

-   Saturation at **2 clients**, peak **526 req/s**; Little's Law
    (W = L/X) matches the measured p50 at every level
-   Capacity under p95 ≤ 80 ms: **526 req/s**; the SLO breaks between
    8 and 16 clients
-   Batch of 100 rows: **0.033 ms per row** vs 2.667 ms for single rows
    (about 80× cheaper)
-   Two workers: capacity **526 → 792 req/s (1.51×)**, not a full 2×

Latency numbers depend on the machine; mine are in `partA/machine.txt`
and the report.

# Part B --- MLflow Registry, Gate and Shadow

**Directory:** `partB/`

Set the tracking store in **every terminal** used for Part B:

``` bash
export MLFLOW_TRACKING_URI=sqlite:///mlflow.db
```

### Gate Tests (B2)

``` bash
pytest partB -v
```

Expected: **18 passed**.

### Register Both Models (B1)

``` bash
python partB/eta_mlflow.py register
```

This logs v1 and v2 as MLflow pyfunc models, registers them as
`eta-model` and sets the aliases `prod → version 1 (v1)` and
`candidate → version 2 (v2)`.

> **Note:** run `register` only once. Every extra run adds two more
> versions.

To see the registry in the browser (optional):

``` bash
mlflow ui --backend-store-uri sqlite:///mlflow.db --port 5000
```

Then open `http://localhost:5000/#/models/eta-model`.

### Promotion Gate (B2)

``` bash
python partB/eta_mlflow.py gate
python partB/eta_mlflow.py gate --min-rel-gain 0.60
```

Expected: `promote: true` with the default thresholds, and
`promote: false` with a 60% gain requirement (only `mae_gain` fails).

### Shadow Comparison (B3)

Terminal 1 (prod):

``` bash
mlflow models serve -m "models:/eta-model@prod" -p 5101 --env-manager local
```

Terminal 2 (candidate):

``` bash
mlflow models serve -m "models:/eta-model@candidate" -p 5102 --env-manager local
```

Terminal 3, once both servers are running:

``` bash
python partB/shadow.py
```

### Results

-   Gate on 2000 fresh rows: MAE **11.96 → 6.10 min** (48.9% better),
    better on both the rush-hour and rain slices, p95 1.3 ms →
    **promote**
-   Shadow on 200 identical requests: mean difference **9.48 min**,
    **35%** of requests differ by more than 10 min, p95 7.3 ms (prod)
    vs 7.6 ms (candidate)

# Part C --- Ray Serve Sticky Canary

**Directory:** `partC/`

`eta_ray.py` deploys `EtaProd` (v1, 2 replicas) and `EtaCandidate`
(v2, autoscaling 1--3 replicas) behind a FastAPI router. Each customer
is placed in an arm with a SHA-256 hash of the `customer_id`, so the
same customer always gets the same model. The header `X-Beta: 1` forces
v2. All replicas use fractional CPUs and fit on 2 CPUs (1.35 at most).

### Run the Verification (C2)

``` bash
python partC/verify_ray.py
```

This starts a 2-CPU Ray instance, deploys the app on port 8100 with
weight 0.2, runs checks (a) to (e) with assertions and ends with
**ALL CHECKS PASSED**. It takes about 1--2 minutes.

### Results

-   (a) candidate share **0.203** with 1000 customers (needed 0.2 ± 0.04)
-   (b) **0** of 200 customers changed arm on a second call
-   (c) **0** of 200 changed arm after redeploying the app
-   (d) weight 0.2 → 0.5: **310** moved to v2, **0** moved back to v1
-   (e) `X-Beta: 1` sent **50/50** requests to v2

# Part D --- Release Gate (Smoke Test)

**Directory:** `partD/`

`smoke_eta.py` runs 8 checks against a live server (health, model
version, sensible ETAs, 422 on bad input, two model-sanity checks,
determinism and order, p95 latency) and exits with **0** if all pass and
**1** otherwise.

Start the Part A server:

``` bash
ETA_MODEL=data/eta_v1.joblib uvicorn eta_app:app --app-dir partA --port 8000 --no-access-log
```

In another terminal:

``` bash
python partD/smoke_eta.py --url http://localhost:8000 --expect-version v1; echo "exit code: $?"
python partD/smoke_eta.py --url http://localhost:8000 --expect-version v2; echo "exit code: $?"
```

Expected: the first run passes **8/8 → GO, exit code 0**; the second
deliberately expects the wrong version and gives **7/8 → NO-GO, exit
code 1**, showing that the gate blocks a bad release.

The four canary abort criteria (metric, threshold, window) are in the
report, section D2.
